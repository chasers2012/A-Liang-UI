# Create Factor Skill

## 目标

在 `apps/api` 中新增一个可用、可测试、可维护的因子，确保：

- 因子定义清晰（含经济含义和计算口径）
- 输入输出结构稳定（字段、类型、单位一致）
- 接入路径完整（实现、注册、调用、文档）
- 至少具备最小验证（样例数据或单测）

## 触发场景

当用户有以下需求时使用本 skill：

- “帮我新增一个因子”
- “实现某个 factor”
- “把某个指标做成可调用因子”
- “在 API 里加一个因子并暴露出去”

## 创建流程

按顺序执行，不跳步。

1. 明确因子规格
2. 设计因子接口
3. 实现核心逻辑
4. 注册并暴露能力
5. 增加验证与说明
6. 自检并交付

## Step 1: 明确因子规格

先写清楚以下信息，信息不全时先向用户确认：

- 因子名称：英文 `snake_case`，语义明确
- 频率：日频 / 周频 / 月频 / 分钟频
- 标的范围：股票 / 期货 / 指数 / 全市场
- 回看窗口：例如 `20`、`60`、`252`
- 缺失值策略：丢弃、前值填充、固定值填充
- 极值处理：不处理 / 截尾 / winsorize
- 标准化：无 / z-score / rank
- 输出单位：原值、百分比或标准分

## Step 2: 设计因子接口

保持接口稳定，优先使用显式参数而不是隐式全局状态。

- 输入：行情数据、可选参数（窗口、阈值、频率等）
- 输出：结构化结果（建议至少包含 `symbol`、`date`、`value`）
- 错误：参数非法或数据不足时，返回明确错误信息

推荐约定：

- 参数名称统一小写下划线
- 窗口参数统一命名为 `window`
- 输出值字段统一命名为 `value`

## Step 3: 实现核心逻辑

实现时遵循“先正确，再优化”：

- 先保证计算定义与规格一致
- 再处理边界：空数据、窗口不足、除零、NaN/inf
- 最后考虑性能：向量化、批量处理、减少重复计算

实现要求：

- 计算逻辑与数据清洗逻辑分离，避免函数过长
- 不在核心计算中写死业务常量，改为可配置参数
- 不吞异常；对可预期错误给出可读报错

## Step 4: 注册并暴露能力

创建因子后，确保系统能发现并调用它：

- 在因子模块中完成导出/注册
- 如果有路由或控制器映射，补齐映射关系
- 若有前端或调用方依赖的类型定义，补齐对应字段
- 更新必要文档，说明参数与返回结构

## Step 5: 自检清单

交付前逐项确认：

- [ ] 因子名称、参数、输出字段命名一致
- [ ] 规格中的窗口/频率/缺失值策略已落实
- [ ] 边界场景有处理（空数据、窗口不足、异常值）
- [ ] 已完成注册，外部可调用
- [ ] 已补充验证（测试或样例）
- [ ] 已更新必要文档

## 最小输出模板

新增因子后，向用户汇报时使用：

```markdown
已完成因子创建：`<factor_name>`

- 计算定义：<一句话说明>
- 关键参数：<window/threshold/frequency 等>
- 输出结构：<symbol, date, value ...>
- 注册位置：<文件路径或模块名>
- 验证方式：<单测/样例>
- 已知限制：<如数据长度要求、适用市场等>
```

## 常见错误

- 只写了计算函数，未完成注册，导致无法调用
- 输出字段命名不统一，调用方解析失败
- 没有处理窗口不足与缺失值，结果不稳定
- 将数据清洗与计算耦合，后续难以维护
